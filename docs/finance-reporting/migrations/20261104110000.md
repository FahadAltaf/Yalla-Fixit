# 20261104110000_finance_refusals_no_retry

A refusal comes back at once (2 Nov). Four functions refused with SQLSTATE 40001 (`serialization_failure`) when the
page was out of date. The database API retries a transaction that fails with 40001, so the same refusal repeated until
the gateway timed out (about two minutes) instead of showing the person a message. Found checking 20261104100000 on the
live database: `finance.mark_invoiceable` on a work order that is not marked hung for 125 s. Nothing was written.

| Function | Refusal that hung |
|---|---|
| `finance.wo_apply_action` | "the work order is X now, not Y" (put on hold / resume from a stale page) |
| `finance.reply_query_thread` | "the query is already closed" |
| `finance.mark_not_invoiceable` | "It is already marked not invoiceable" |
| `finance.mark_invoiceable` | "It is not marked not invoiceable" |

Same functions, rules and words; the refusal's code is now `check_violation` (23514), which the portal already shows
as a message. `wo_apply_action`'s message also says to reload. `20261104100000_…sql` itself was corrected the same way,
so a fresh database never gets the retrying code.

Live-safe: `CREATE OR REPLACE` of four functions in schema `finance`, same signatures and grants. Idempotent (applied
twice on a throwaway Postgres 15; each refusal returned at once). The old queue functions of 20261021100000 also use
40001, but nothing calls them any more.

## Before applying: anything still looping?

```sql
select pid, state, now() - query_start as running, left(query, 120) as query
from pg_stat_activity
where query ilike '%mark_invoiceable%' or query ilike '%wo_apply_action%' or query ilike '%reply_query_thread%';
```

Expect no rows (the API gives up when the gateway does). If a row has been running for minutes:
`select pg_cancel_backend(<pid>);`

## Pre-check (expect a number above 0)

```sql
select count(*) from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'finance' and p.proname in ('wo_apply_action', 'mark_invoiceable', 'mark_not_invoiceable', 'reply_query_thread')
  and pg_get_functiondef(p.oid) like '%serialization_failure%';
```
