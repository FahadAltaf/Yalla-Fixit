# 20261105100000_close_anon_table_access

Sami's report (2 Nov 2026): permissions could be read and changed without signing in. Three ways in:

| Way in | State on 3 Nov | Fix |
|---|---|---|
| `/api/role-access` with no session | Checked since 07a3e12 (2 Nov): 401 signed out, 403 without the Permissions right | Code, already on `main` |
| `/api/graphql` (forwards any query with the anon key, no session) | Open: roles, permission rows and profiles could be listed, written and deleted | Code: forwards only its allowlist (the portal's settings query) |
| The anon key itself, called straight at the database. It ships in the inspector app (`EXPO_PUBLIC_SUPABASE_ANON_KEY`) | Open, see below | **This migration** |

What the anon key reached on production, read-only on 3 Nov: `roles` 5 rows, `role_access` 99, `user_profile` 19,
`schedule_audit_events` 1,234, `todos` 4; pg_graphql offered it insert, update and delete on those tables and on
`password_resets`, `todo_attachments` and `todo_comment_mentions`. With insert on `password_resets` a reset token
could be planted for any account (the code now keys the token hash with a server secret as well, so a planted row
no longer matches).

So `20261005150000` (audit log) and `20261006161000` (todos) are **not in effect** on production, although this log
recorded them as applied, and `20261006160000` (role tables) was held. This file is their table parts again plus
the reset-token and to-do child tables. Idempotent: safe whatever part of them already ran (applied twice on a
throwaway Postgres 15, `scripts/db-harness/checks/95_anon_closed.sql`: 11 checks pass; before it, the anon role
could insert a permission row).

## Apply when

**Only once the live portal runs `main` at 07a3e12 or later** (your push d512bb3 includes it). Older code saved users,
roles and permissions from the browser with the anon key, and those screens would stop saving. The current code
reads and writes all eight tables with the service role, which REVOKE does not touch. The inspector app reads none of
them.

Check the live site first (signed out, read-only; expect 401):

```bash
curl -s -o /dev/null -w "%{http_code}\n" "https://<live portal>/api/role-access?operation=getByRole&roleId=00000000-0000-0000-0000-000000000000"
```

200 means the old code is still live: deploy first.

## Pre-check (read-only; expect anon rows, which is the hole)

```sql
select table_name, grantee, string_agg(privilege_type, ',' order by privilege_type) as privileges
  from information_schema.role_table_grants
 where table_schema = 'public' and grantee in ('anon', 'authenticated')
   and table_name in ('roles','role_access','user_profile','schedule_audit_events','todos',
                      'todo_attachments','todo_comment_mentions','password_resets')
 group by 1, 2 order by 1, 2;
```

## Apply

Paste `supabase/migrations/20261105100000_close_anon_table_access.sql` into the SQL editor and run it once.

## Post-check

The pre-check query again. Expect exactly three rows, no anon row:

```
role_access  | authenticated | SELECT
roles        | authenticated | SELECT
user_profile | authenticated | SELECT
```

Then in the portal: sign in, open Users, Roles and Permissions, change one permission and change it back, and send
yourself a password reset. Signed out, the anon key now gets `42501` on `roles`.
