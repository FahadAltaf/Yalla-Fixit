Verdict

Every proposal this module has ever produced is priced at zero

The pricing engine is wired to constants that were never filled in.

All 12 AMC services carry unitRate: 0, left behind a TODO(pricing) comment. Price is computed as unit rate × units × frequency, so every line item evaluates to AED 0.00 — and so do the subtotal, the discount, the 5% VAT and the grand total. I confirmed this against production: all 10 submissions have final_price = 0, including the one that was marked generated and had both a proposal and a contract PDF produced from it.

Orientation

What the module does

A three-step wizard that turns property and customer details into a branded AMC proposal or contract PDF, saved per user so drafts can be resumed.

  • Step 1 — Property & Customer. Category (residential/commercial), unit type (villa/apartment/office), address, customer identity, two mandatory coordination contacts, contract dates, payment terms, proposal number.
  • Step 2 — Package & Services. One of four residential packages (Basic AED 95 → Elite AED 250 per month) or a commercial monthly rate, plus a service table with per-line units and frequency.
  • Step 3 — Review & Generate. Totals summary and PDF generation.

Services are typed by how they bill — covered, unlimited, ppm, handyman, fixed — which drives both the default frequency and how it prints ("2 per year", "12 hours per year", "Covered"). Villa-only services are filtered out for apartments and offices. PDFs are rendered client-side by html2canvas into jsPDF, with a measure-then-slice pagination pass so page breaks land between sections.

Findings · severity order

Eight issues, two of them blocking

F1Critical

All service unit rates are zero, so every total is zero

AMC_SERVICES defines 12 services. Every one has unitRate: 0, under a comment marking it as unfinished. Nothing downstream guards against it, so the wizard happily generates a signed-looking contract for AED 0.00.

// amc-constants.ts:43 // TODO(pricing): team to fill unit rates from pricing sheet // — all default to 0 until then. $ grep -o "unitRate: [0-9.]*" amc-constants.ts | sort | uniq -c 12 unitRate: 0 // amc-pricing.ts:23 return service.unitRate * row.units * row.frequency; // → 0
ImpactThe module cannot produce a commercially valid document. Confirmed on all 10 live submissions.
FixPopulate unit rates from the pricing sheet, and block generation when an included service still has a zero rate.
F2Critical

Customer records are readable by anyone with the public key

amc_submissions has RLS enabled with a policy of USING (true) WITH CHECK (true) for role public. The API route carefully scopes every query by owner_id and gates on an email allowlist — but PostgREST is reachable directly, so none of that applies. I verified this with the anon key alone, the same key shipped to every browser.

GET /rest/v1/amc_submissions?select=... (anon key only) → HTTP 206 · total rows visible: 10

The rows expose the customer JSONB: name, phone, email and both coordination contacts. The policy also permits writes, so records can be altered or deleted by an unauthenticated caller.

ImpactCustomer PII disclosure, and unauthenticated modification of contract records.
FixReplace the blanket policy with owner_id = auth.uid(), or revoke the table from anon entirely and let the service-role API remain the only path.
F3High

The commercial monthly rate is required, then discarded

For commercial properties the schema refuses to advance without customMonthlyPrice > 0. That value is validated, mapped, persisted and round-tripped — and never read by any pricing function. It appears in seven places; none is a calculation.

amc-types.ts:61 validates it (required, commercial) amc-submission-mapper stores + restores it package-services-step renders the input amc-pricing.ts ← never referenced
ImpactCommercial quotes ignore the only number the user was forced to supply.
FixDecide whether commercial pricing is rate-driven or line-driven, then wire the chosen input into calculateAmcTotals.
F4High

Package selection is decorative

The four residential packages advertise AED 95 / 125 / 200 / 250 per month. monthlyPrice is rendered in the package card and used nowhere else. calculateAmcTotals sums service rows only, then derives a monthly figure as finalPrice / 12 — so the number shown on the card and the number on the PDF are unrelated.

Picking a package does change ppmVisitsPerYear and handymanHoursPerYear, which set default frequencies. That part works. The headline price does not.

ImpactA customer told "Elite, AED 250/month" receives a document quoting a different figure.
FixEither treat the package price as the contract value, or drop it from the card so it stops implying a promise.
F5Medium

Access is a hardcoded email allowlist, not a role

Five addresses in amc-constants.ts:310 decide who sees the module. The same function gates the client nav and the API route, so at least the two agree — but the list lives in a component file that ships to the browser, and changing who has access means a code change, a review and a deploy.

Every other module in the app uses role_access with a ResourceType and per-action permissions, administered from the Permissions screen. AMC is the exception.

ImpactAccess changes need an engineer; the allowlist is visible in the client bundle; staff turnover leaves stale entries.
FixAdd an AMC resource to the permission system and gate on it, matching the other modules.
F6Medium

Proposal numbers are random with no uniqueness check

AMC-{year}-{random 1000–9999}, generated in the browser, with no database lookup and no unique constraint on the column. That is 9,000 values per year, so by the birthday bound a collision becomes more likely than not at roughly 112 proposals in a year.

// amc-constants.ts:211 const suffix = String(Math.floor(Math.random() * 9000) + 1000); return `AMC-${year}-${suffix}`;

The number is the customer-facing reference and the PDF filename, so a collision means two different contracts sharing an identifier.

ImpactDuplicate contract references; overwritten downloads.
FixAllocate server-side from a sequence and add a unique constraint.
F7Low

Submissions can be created and edited, never deleted

The route exports GET, POST and PUT. There is no DELETE, and the submissions list offers Edit and two View actions but no remove. Nine of the ten live rows are abandoned drafts.

ImpactThe list accumulates test and abandoned drafts with no way to clear them.
FixAdd a soft-delete (archived_at) and a row action, filtering archived rows from the default view.
F8Low

No delivery step — the PDF is a manual download

There is no email path in the module. The customer's address is collected and validated at step 1, then only used to populate the document. Sending means downloading the file and attaching it by hand, outside the system — so there is no record of what was sent or when.

Worth noting the codebase already has the pieces: the quotation module sends via Resend, and lib/server/send-email.ts landed recently on this branch.

ImpactNo audit trail of customer delivery; the recorded status says "generated", never "sent".
FixAdd a send action reusing the existing mail helper, and record sent_at.

Credit where due

What holds up well

  • Separation of concerns is genuinely good. Pricing, constants, types, mapping and PDF rendering are separate modules with no circular dependencies. The zero-rate bug is a one-line fix precisely because of this.
  • The autosave queue is carefully built. Saves are chained through a promise queue with a reference count, and status is deliberately not reset when a user steps backwards — with a comment explaining why. That is a real bug someone found and fixed properly.
  • Validation is thorough. Cross-field rules via superRefine cover end-before-start dates, at-least-one-service, and category-conditional requirements, with step-scoped triggers so users aren't shown errors for fields they haven't reached.
  • The PDF pagination is the sophisticated part. It measures the rendered layout, then computes slice offsets so breaks fall between scope sections instead of mid-table.
  • The UI matches the rest of the app — Card, Table, EmptyState, Skeleton, StatusBadge and DropdownMenu row actions, consistent with the other extensions.

One open question I couldn't answer from the code: should an AMC be priced from the package (a flat monthly fee, services defining scope rather than cost), or from the service lines (rates × frequency, package as a preset)? The module currently implements the second and displays the first. Both F3 and F4 collapse into a single change once that's settled.
